# @agorail-labs/scq-reference 1.0.0-rc.3 — release candidate notes

**Status: CANDIDATE — not a stable release. Published under the
`next` dist-tag only; `latest` remains on 1.0.0-rc.2 until this
candidate has been tried. The specification remains SCQ v0.6.2.**

## What this candidate is

The third release candidate for SCQ's stable core. Over
1.0.0-rc.2 it carries one functional fix: durable receipt replay
(§6.10) from an already-open store instance. No export, schema,
or protocol changes.

## Changes from 1.0.0-rc.2

- Fixed: `DurableQuoteStore.recordedReceipt()` served the
  in-memory map loaded at open, while attempts are read from
  SQLite. With two instances sharing one database, an instance
  opened before another worker recorded a receipt could read the
  terminal attempt yet miss the receipt — standalone replay threw
  `DispatchBlockedError` naming COMMITTED_AND_VERIFIED, and the
  intent bridge returned BLOCKED / NO_RECORDED_RECEIPT, while a
  fresh instance replayed correctly (PR #93).
- The lookup now reads durable state at replay time and
  validates the record set before serving the immutable original
  recorded receipt: the quote row's integrity checksum,
  persistence-codec decoding, the recorded receipt's identity
  digest, the parent store's restore coherence validation, and
  cross-record agreement between the quote row and its receipt
  record. A quote row carrying a recorded receipt whose
  companion receipt row is missing is inconsistent storage and
  fails explicitly; genuine absence is unchanged, and a failed
  lookup never falls back to in-memory state and never
  authorizes a dispatch. The lookup is read-only and adopts
  nothing into the instance's in-memory or CAS state.
- Coverage: test68 (16 tests over real temporary SQLite,
  including a separate already-open process); full suite of 936
  tests passing on Node 22/24/26 in CI.
- Reported by Fabio, who supplied the reproductions and the
  five-case bridge observations that pinned the behavior.

## Known limitations

- The core trusts adapter-established classification (G-01).
- No live provider dispatch; no exactly-once provider execution
  or cross-provider atomicity is claimed.
- The local-pack checksum discrepancy remains unexplained; this
  candidate is produced through the CI release workflow, whose
  recorded hashes are the artifact of record.
- Independent review is a pending gate — see
  `docs/RELEASE-QUALIFICATION.md`.
