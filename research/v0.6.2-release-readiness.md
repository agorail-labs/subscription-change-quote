# SCQ v0.6.2 — Release-Readiness Assessment

Status: **candidate-supporting document for a DRAFT specification.** v0.6.2 is not
approved, published, or released; v0.6.1 remains the current specification.

Five **independent** assessments follow. They are independent on purpose: strength in one
says nothing about the others.

> **Standing caution.** A green CI run is not evidence of specification approval. A
> merged PR is not a release. Neither is evidence of production compatibility with any
> provider, and neither is authorization for a live commit. The repository's history is
> full of green, merged work (PRs #8–#20) while the test-site commit decision remained
> NO-GO throughout — that is the system working as designed, not a contradiction.

## A. Technical implementation readiness — PARTIAL

The v0.6.2 normative machinery is implemented once, in the shared core and store, and is
in force for all five adapters: three-state determinacy with N/A purity (BC-1/BC-2,
PR #8/#19), the incurred definition of `immediate` (PR #10/#11 corrections), committed-
evidence provenance and reconciliation precedence (PR #19), the four-class outcome
taxonomy with retry discipline (PR #16/#17), the §6.12 state-verification hook
(PR #18), and the durable write-ahead layer (PR #17). The full suite stands at
612/612 on `main` (`6f56b05`) and every rule in the candidate's Appendix B maps to
implementation plus pinning tests in `conformance/v0.6.2-traceability.md`.

Why PARTIAL and not PASS: two rules are assessed PARTIAL in the traceability matrix —
snapshot determinacy is emitted but never consumed (V62-DET-08 / gap G-07), and three
adapters' state establishments are adapter-owned equivalents rather than consumers of
the shared hook (V62-SV-02 / gap G-08) — and the inherited conformance gaps G-2/G-5/G-6
remain open (G-09). None of these is a known unsafe behaviour; all fail closed. They are
completeness gaps in the implementation/evidence, recorded rather than resolved by
fiat.

## B. Specification approval readiness — PARTIAL

The candidate is complete and reviewable: full normative text preserving v0.6.1's
structure, a clause-by-clause delta (Appendix A), a stable rule index (Appendix B),
traceability, a BC-1…BC-6 migration guide, a provider audit, and this gap register. A
maintainer can approve or reject it on the merits from these documents alone.

Why PARTIAL and not PASS: approval is a governance act that has not occurred, and four
contested choices are explicitly undispositioned — EXACT source authentication (G-01),
committed-role provenance basis (G-02), multi-change N/A licensing (G-03), and scheduled
effective-time evidence sufficiency (G-04). Additionally, the candidate sits on a
freeze-guarded path: `check-frozen-surface` fails on the PR-12 branch **by design**
until the maintainer applies the `protocol-change-approved` label after independent
review. PR-12 does not apply that label, does not bump any version, and does not present
the candidate as approved.

**What must happen before the specification can be approved (recommendation):**
(1) maintainer dispositions G-01–G-04 in the approval record (ratify the implemented
semantics or amend the text — either is legitimate; silence is not); (2) maintainer
confirms the §9 unresolved list (U-1…U-12) is acceptable as the approved spec's open
items; (3) the `protocol-change-approved` label is applied by the maintainer and the
freeze guard goes green; (4) only after merge, a separate approved step updates the
README's current-version line and any package metadata. Until (1)–(3) happen, the
correct status of v0.6.2 is DRAFT.

## C. Reference package readiness — PASS (as an unpublished reference package)

The package `@arjun2075/scq-reference` builds cleanly from a fresh `npm ci`
(Node 22.14 locally; CI matrix Node 20/22), the full test suite passes, `smoke:pack`
produces and smoke-tests the tarball, and the demos (`demo`, `demo:commit`) run. Its
published-status facts are unchanged and accurate: `private: true`, version `0.1.0`,
README states SCQ v0.6.1 as current with the v0.6.2 work described as
candidate/in-progress, and the README's limitations section still matches reality (no
live commit path is enabled; the live adapter is experimental; determinacy limits are
stated). PR-12 changes none of these.

PASS here means exactly one thing: the package is a correct, buildable, unpublished
reference implementation of the *current* (v0.6.1) specification plus merged v0.6.2
machinery. It is not a release of v0.6.2, and unpublishing guards (`private: true`) stay
in place until a separately approved release decision.

## E. Production readiness — BLOCKED

There is no production evidence of any kind: no live commit has ever been executed
against any provider; the error-classification allowlist has never met a real error
surface (G-10); the origin manifest has no external trust anchor (G-05); the durable
layer's guarantees are stated for a single-writer deployment that has never been
operated; no provider has reviewed, endorsed, or adopted SCQ; and the specification
itself remains an unapproved draft (assessment B). Production use of this reference
implementation for real billing mutations would be unjustified on the current record,
regardless of test counts.
