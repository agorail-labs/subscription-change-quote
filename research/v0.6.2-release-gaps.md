# SCQ v0.6.2 — Release Gap and Discrepancy Register

Status: **candidate-supporting document for a DRAFT specification.** v0.6.2 is not
approved, published, or released; v0.6.1 remains the current specification.

Every material discrepancy found between the v0.6.2 candidate's requirements and the
existing implementation (or its evidence) is recorded here. Classification vocabulary:
normative ambiguity / implementation defect / test-conformance gap / migration issue /
provider limitation / missing external evidence / release governance requirement.

**Contested choices are recorded as OPEN DECISION.** PR-12 does not resolve them, and
the candidate spec was *not* silently written to fit existing behaviour where a choice is
contested: the spec states the implemented rule and cross-references the open decision
(spec §9 U-9…U-13 mirror G-01, G-02, G-04, G-05, G-13 below).

Severity: HIGH = blocks specification approval or a live-commit decision; MEDIUM = must
be dispositioned (fixed, pinned, or explicitly accepted) before approval; LOW = record
and track.

## G-01 — EXACT source authentication (OPEN DECISION)

- **Classification:** normative ambiguity / missing conformance mechanism.
- **Affected clause:** spec §3.11, §6.13 (rule V62-EVD-01); BC-1 note §9.
- **Implementation path:** `core/scq-engine.ts` · committed-role assessment reads the
  `CommittedFigureSource` label; `core/types.ts` · the source union.
- **Counterexample (pinned, not hypothetical):** test35.29 — an EXACT-shaped committed
  assertion carrying the `defined_equal_exact` label but no establishing evidence is
  refused (UNVERIFIED), *because that fixture also lacks the provenance the gate
  requires*; test35.28 — the same label *with* the required provenance establishes. The
  pair proves the boundary precisely: the core judges the label's **classification**,
  and nothing in the core can authenticate that an EXACT contract actually stands behind
  the label. A buggy or dishonest adapter can mint the label.
- **Severity:** HIGH for specification approval (the candidate's committed-evidence story
  rests partly on this label); does not affect any live decision today (no live commit
  is authorized).
- **Recommended resolution (maintainer decision):** either (a) accept classification-only
  semantics permanently and strengthen §3.11's non-claim wording at approval time, or
  (b) require EXACT eligibility to be established by an authenticated capability (e.g.
  adapter-registered coverage attested at wiring time, as Chargebee-live's durable
  wiring checks already do for store/coordinator binding). Do not resolve by editing
  tests.

## G-02 — Committed-role provenance basis asymmetry (OPEN DECISION)

- **Classification:** normative ambiguity.
- **Affected clause:** spec §6.13 (rule V62-ENV-05); BC-1 note §8.
- **Implementation path:** `core/scq-engine.ts` · `assessDimensionSide` — quote and
  revalidated roles treat provenance-or-note as the establishing basis; the committed
  role requires the `committedSource` field itself, and an absent field leaves the
  dimension UNKNOWN *even when a provenance note is present*.
- **Counterexample:** a committed figure labelled `provider_actual` in its note but
  serialized without `committedSource` enforces as UNKNOWN and reconciles UNVERIFIED,
  while the mirror-image quote-side figure establishes. The BC-1 review recorded this
  stricter committed-role reading as the conservative choice; it has never been
  explicitly ratified as protocol intent.
- **Severity:** MEDIUM (fail-closed direction; surprises integrators, cannot cause a
  false pass).
- **Recommended resolution (maintainer decision):** ratify the asymmetry in the approved
  spec text, or align the roles. Either way the decision belongs in the approval record,
  not in code churn during candidacy.

## G-03 — Multi-change quotes can never license NOT_APPLICABLE (OPEN DECISION)

- **Classification:** normative ambiguity (design consequence, possibly intended).
- **Affected clause:** spec §3.10 (rule V62-DET-05); BC-1 note §8.
- **Implementation path:** `core/scq-engine.ts` · `authoritativeAction` returns no single
  context for multi-change sets, so no N/A dimension of a multi-change quote can ever be
  licensed (pinned at test35, lines 338–346).
- **Counterexample:** a two-change set {REMOVE_ITEM, CANCEL-at-term-end} whose cancel
  dimension is genuinely not applicable cannot represent that fact; it must use
  DETERMINED 0 (if the semantics fit) or UNKNOWN (and fail an envelope gate).
- **Severity:** MEDIUM-LOW (fail-closed; expressiveness cost only).
- **Recommended resolution (maintainer decision):** confirm the blanket rule as intended
  v0.6.2 semantics (the candidate states it as such), or open a future-revision item for
  per-dimension action contexts. Not to be "fixed" by implementation change during
  candidacy.

## G-04 — Scheduled effective-time evidence sufficiency (OPEN DECISION)

- **Classification:** normative ambiguity.
- **Affected clause:** spec §6.12 (rule V62-SV-06), §9 U-7/U-11.
- **Implementation path:** `core/state-verification.ts` · cancellation checks (SV2/SV4/

- **Counterexample:** two observations of the same scheduled cancellation — one carrying

## G-05 — Chargebee origin-manifest trust-model limits (OPEN DECISION)

- **Classification:** missing external evidence / release governance requirement.
- **Affected clause:** pilot-layer (issue #12), feeding spec §9 U-12; PR-11 note
  §§11–12.
- **Implementation path:** `research/chargebee-pilot/origin-manifest.ts` (v2 records:
  complete-record digest + `prevRecordDigest` chain + once-only writer).
- **Concrete limits (accepted by the reviewer when PR #20's hardening was approved):**
  the manifest provides tamper-**evidence** against ordinary file modification —
  substitution of the record's own site field, second records, deletion, and reordering
  are all detected (test41). It provides **no** protection against a privileged writer
  who controls both the manifest and the store (they can rewrite the chain), **no**
  external trust anchor (no countersignature, no WORM storage), and **no** authenticated
  creation time or issuer identity. A determined insider forgery is undetectable by this
  mechanism alone.
- **Severity:** HIGH for any future live-commit decision (Condition 3's origin evidence
  rests on this manifest); LOW for specification approval (the manifest is pilot-layer,
  not protocol).
- **Recommended resolution:** before any test-site commit decision, either add an
  external anchor (countersignature or append-only external log) or record an explicit
  maintainer risk acceptance of the insider-forgery limit. Named as subsequent work in
  the PR-11 note; not built in PR-12.

## G-13 — Confirmed-non-execution re-dispatch doctrine (OPEN DECISION)

- **Classification:** normative ambiguity (doctrine choice surfaced by PR #21 review
  finding SPEC2: the candidate's original §3.12/§8 text said CONFIRMED_NON_EXECUTION is
  retried "as a new quote", contradicting the merged ledger).
- **Affected clause:** spec §3.12, §6.15, §6.16 (rule V62-DUR-05); BC-6; spec §9 U-13.
- **Implementation path:** `store/durable-store.ts` · `beginDispatch` — the
  CONFIRMED_NON_EXECUTION branch re-arms the SAME attempt row under the same quote and
  idempotency key (state → DISPATCHING, re-dispatch recorded in attempt history),
  introduced deliberately in PR #17 and hardened by its finding D2 (same-subscription
  exclusion re-checked inside the same transaction before re-arming). Verified against
  the code for this correction: key→request-hash check, key bound to one
  quote/subscription/provider/site (D2/D5), DISPATCHING and unresolved-INDETERMINATE
  blocks, terminal COMMITTED_* serving its recorded outcome, and — upstream on the
  commit path — `core/scq-engine.ts` · `validateCommit` applying expiry
  (QUOTE_EXPIRED) and subscription-fingerprint (QUOTE_STALE) validation on every
  presentation before `beginDispatch` is reached, so a stale quote cannot override
  those preconditions to reach the re-dispatch gate.
- **Doctrine as now specified (the implemented one):** one same-quote, same-key
  re-dispatch per CONFIRMED_NON_EXECUTION settlement, gated on identical canonical
  request + hash, unchanged binding, the in-transaction exclusion re-check, and the
  ordinary expiry/fingerprint preconditions. INDETERMINATE is never re-armed.
  Pinning tests (none weakened): test29.9 (D2b, legitimate re-dispatch succeeds),
  test29.8 (D2a, blocked while a same-subscription attempt is unresolved), test29.10
  (D2c, key never re-associated), test27.20 (same key + different request refused),
  test27.10/27.12 + test28.2 (INDETERMINATE never re-arms), test28.1 (committed
  receipt replays, no second dispatch).
- **Security tradeoff, stated plainly:** the same-key re-dispatch is safe ONLY because
  non-execution was independently confirmed pre-effect (the L2/L3 classification gates
  are load-bearing: an ambiguous failure settles INDETERMINATE and can never reach
  this branch), and because the re-presented request is bit-identical under the
  canonical hash. The risk it accepts: a single idempotency key can authorize a second
  dispatch, so any future weakening of the pre-effect confirmation standard silently
  widens into a double-mutation path. The alternative — requiring a fresh quote and
  fresh key for every retry — buys freshness (a new TTL window and a newly derived
  fingerprint/quote) and a simpler invariant (one key, one dispatch, ever), at the
  cost of a separately reviewed, gated implementation change to the durable store and
  the loss of the original attempt's audit continuity.
- **Severity:** MEDIUM-HIGH for specification approval — the text and the code now
  agree, but the doctrine is a maintainer choice, not a drafting choice.
- **Recommended resolution (maintainer decision):** ratify the implemented doctrine in
  the approval record, OR direct the fresh-quote/key alternative to be implemented in
  a separate gated PR before approval. Do not resolve by weakening or deleting the
  pinning tests.

## Review corrections (SPEC1 / SPEC2 / DOC1) — PR #21 review round

Recorded here because these documents are living drafts; the corrections are integrated

errata. Documentation-only round: no code changed, no test changed or weakened.

- **SPEC1 (EXACT deep-equality contradiction) — corrected.** The candidate's §3.9 had
  carried v0.6.1 §3.8's whole-object "MUST deep-equal" wording forward, where it

  committed-side provenance (`provenance.committedSource: "defined_equal_exact"` —
