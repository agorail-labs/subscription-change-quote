## G-01 — EXACT source authentication (OPEN DECISION)

- **Classification:** normative ambiguity / missing conformance mechanism.
- **Proposed disposition (pending ratification):** PROPOSED: RATIFY, with explicit
  trust limitation (the core trusts adapter-established classification; it does not
  independently authenticate provider events; no stronger assurance is claimed). See
  the Maintainer decision record above. Not ratified; this entry remains open.
- **Affected clause:** spec §3.11, §6.13 (rule V62-EVD-01); BC-1 note §9.
- **Implementation path:** `core/scq-engine.ts` · committed-role assessment reads the
  `CommittedFigureSource` label; `core/types.ts` · the source union.
- **Counterexample (pinned, not hypothetical):** test35.29 — an EXACT-shaped committed
  assertion carrying the `defined_equal_exact` label but no establishing evidence is
  refused (UNVERIFIED), *because that fixture also lacks the provenance the gate
  requires*; test35.28 — the same label *with* the required provenance establishes. The
  pair proves the boundary precisely: the core judges the label's **classification**,
  and nothing in the core can authenticate that an EXACT contract actually stands behind
  the label. A buggy or dishonest adapter can mint the label.
- **Severity:** HIGH for specification approval (the candidate's committed-evidence story
  rests partly on this label); does not affect any live decision today (no live commit
  is authorized).
- **Recommended resolution (maintainer decision):** either (a) accept classification-only
  semantics permanently and strengthen §3.11's non-claim wording at approval time, or
  (b) require EXACT eligibility to be established by an authenticated capability (e.g.
  adapter-registered coverage attested at wiring time, as Chargebee-live's durable
  wiring checks already do for store/coordinator binding). Do not resolve by editing
  tests.

## G-05 — Chargebee origin-manifest trust-model limits (OPEN DECISION)

- **Classification:** missing external evidence / release governance requirement.
- **Affected clause:** pilot-layer (issue #12), feeding spec §9 U-12; PR-11 note
  §§11–12.
- **Implementation path:** `research/chargebee-pilot/origin-manifest.ts` (v2 records:
  complete-record digest + `prevRecordDigest` chain + once-only writer).
- **Concrete limits (accepted by the reviewer when PR #20's hardening was approved):**
  the manifest provides tamper-**evidence** against ordinary file modification —
  substitution of the record's own site field, second records, deletion, and reordering
  are all detected (test41). It provides **no** protection against a privileged writer
  who controls both the manifest and the store (they can rewrite the chain), **no**
  external trust anchor (no countersignature, no WORM storage), and **no** authenticated
  creation time or issuer identity. A determined insider forgery is undetectable by this
  mechanism alone.
- **Severity:** HIGH for any future live-commit decision (Condition 3's origin evidence
  rests on this manifest); LOW for specification approval (the manifest is pilot-layer,
  not protocol).
- **Recommended resolution:** before any test-site commit decision, either add an
  external anchor (countersignature or append-only external log) or record an explicit
  maintainer risk acceptance of the insider-forgery limit. Named as subsequent work in
  the PR-11 note; not built in PR-12.

## G-07 — Snapshot determinacy is emitted but never consumed

- **Classification:** test-conformance gap / partial implementation.
- **Affected clause:** spec §3.10 (rule V62-DET-08).
- **Implementation path:** `core/types.ts` · `SubscriptionSnapshot.billing.
  recurringAmountState`; nothing in the engine, store, or adapters reads it.
- **Counterexample:** a snapshot labelled DETERMINED beside a recurring figure the
  producing fallback actually estimated would mislead a reader; adapters currently label
  honestly (test25 pins a fallback-computed snapshot as UNKNOWN), but no test pins a
  *consumer* refusing a wrong label, because there is no consumer.
- **Severity:** LOW-MEDIUM.
- **Recommended resolution:** either consume the field in a named check in a future
  revision, or mark it explicitly informative in the approved spec. PR-12 records the
  PARTIAL assessment in the traceability matrix rather than inventing a consumer.
- **Post-#29 investigation (Oct 30, 2026) — decision: DESCRIPTIVE; PARTIAL retained.**
  Producer map (all five snapshot builders set the field at construction):
  Stripe/Paddle compute `totalRecurring = Σ unitAmount × quantity` over the modeled
  items and label DETERMINED; Zuora computes the same sum over rate-plan charges and
  labels DETERMINED; Chargebee-sim sums catalog-priced items and, where an item price
  is unestablished, WITHHOLDS the figure and labels UNKNOWN; Chargebee-live sums only
  provider-stated item amounts (the pre-migration unit_price×quantity / absent⇒0
  fallback was removed in the migration) and likewise withholds + labels UNKNOWN.
  Consumer map: NO reader exists — the engine, store, and adapters never read
  `recurringAmountState`, and no enforcement path reads a snapshot's `recurringAmount`
  either; the snapshot billing fields actually consumed are `currency` and `cadence`
  (§6.19 unit comparability; cadence checks). Every effect's determinacy is derived
  at effect construction from that effect's own evidence (Chargebee-live derives its
  committed recurring determinacy from its own strict post-commit sum, never from a
  snapshot), and the §3.10 cancellation candidate is sourced from the stored quote's
  committed effect, not from any snapshot. The historical counterexample above (a
  DETERMINED label beside a fallback-estimated figure) is closed at the producer
  side: the estimating fallbacks no longer exist, and producers withhold the figure
  when they cannot establish it. The rule as written (V62-DET-08) mandates that the
  snapshot figure CARRY its state — an emission/labelling requirement, which is
  implemented — and no clause makes the label an enforcement input; §3.10's
  enforcement machinery operates on `CommercialEffect` determinacy records, a
  different type. Inventing a consumer would create behaviour the specification
  does not require. **What closing this row requires (maintainer decision, not
  enacted here):** either (i) amend the v0.6.2 spec to mark the field explicitly
  informative (a normative-text change; freeze-guarded; needs
  `protocol-change-approved`), after which the row can be reclassified on the
  amended rule, or (ii) direct a named enforcement consumer in a future revision,
  with failing-first tests. Until then the field's semantics are as documented in
  the traceability row and the field remains descriptive; PARTIAL stands.

  (retain same-quote/key re-dispatch only following independently confirmed

  record above. Not ratified; this entry remains open.

- **Implementation path:** `store/durable-store.ts` · `beginDispatch` — the
  CONFIRMED_NON_EXECUTION branch re-arms the SAME attempt row under the same quote and
  idempotency key (state → DISPATCHING, re-dispatch recorded in attempt history),
  introduced deliberately in PR #17 and hardened by its finding D2 (same-subscription
  exclusion re-checked inside the same transaction before re-arming). Verified against
  the code for this correction: key→request-hash check, key bound to one
  quote/subscription/provider/site (D2/D5), DISPATCHING and unresolved-INDETERMINATE
  blocks, terminal COMMITTED_* serving its recorded outcome, and — upstream on the
  commit path — `core/scq-engine.ts` · `validateCommit` applying expiry
  (QUOTE_EXPIRED) and subscription-fingerprint (QUOTE_STALE) validation on every
  presentation before `beginDispatch` is reached, so a stale quote cannot override
  those preconditions to reach the re-dispatch gate.

  re-dispatch per CONFIRMED_NON_EXECUTION settlement, gated on identical canonical
  request + hash, unchanged binding, the in-transaction exclusion re-check, and the
  ordinary expiry/fingerprint preconditions. INDETERMINATE is never re-armed.

  test27.10/27.12 + test28.2 (INDETERMINATE never re-arms), test28.1 (committed
  receipt replays, no second dispatch).

  non-execution was independently confirmed pre-effect (the L2/L3 classification gates

  this branch), and because the re-presented request is bit-identical under the
  canonical hash. The risk it accepts: a single idempotency key can authorize a second

  fingerprint/quote) and a simpler invariant (one key, one dispatch, ever), at the
  cost of a separately reviewed, gated implementation change to the durable store and
  the loss of the original attempt's audit continuity.
- **Severity:** MEDIUM-HIGH for specification approval — the text and the code now

- **Recommended resolution (maintainer decision):** ratify the implemented doctrine in
  the approval record, OR direct the fresh-quote/key alternative to be implemented in
  a separate gated PR before approval. Do not resolve by weakening or deleting the
  pinning tests.

## G-22 — Strict plain-object validation for the acceptance envelope (OPEN DECISION)

- **Classification:** specification/implementation mismatch — the specification is
  corrected in the review round; the stricter rule is undecided.
- **Proposed disposition (pending ratification):** PROPOSED: DEFER (current
  own-property validation is documented, as corrected; tightening requires a
  separate tested code change). See the Maintainer decision record above. Not
  ratified; this entry remains open.
- **Affected clause:** spec §6.18 (rule V62-RTV-03).
- **Finding:** the candidate's §6.18 required a supplied `acceptanceEnvelope` to be
  "a plain object". The implemented check (`core/scq-engine.ts` ·
  `envelopeShapeProblem`) accepts any non-null, non-array object: it refuses own
  enumerable keys outside the three named bounds and reads each bound via own
  properties only; it does NOT inspect the object's prototype. The consequence is
  three-way: supported bounds carried as OWN properties are honored (a class
  instance with its own valid `maxRecurringIncrease` has that bound applied);
  inherited bounds are ignored; and a non-plain object with no supported own bounds
  — a `Date` or `Map` instance carrying no own fields — passes the shape check and
  receives zero tolerance (the missing-bounds default of §6.13). In short: a
  non-plain object with no supported own bounds receives zero tolerance; supported
  own bounds are honored, and inherited bounds are ignored. The
  review round corrected the SPECIFICATION to state the implemented acceptance shape
  precisely (SPEC4); no code changed.
- **Why the stricter rule is a decision, not a correction:** enforcing
  plain-objectness (a prototype check) changes behaviour in a freeze-guarded file
  (`reference/src/core/scq-engine.ts`): envelope values currently accepted — class
  instances or built-in objects carrying no own fields — would be refused. It
  therefore requires its own reviewed code PR with failing-first regression tests,
  plus maintainer ratification.
- **Interim exposure:** bounded by the own-property discipline (P15-2): only the
  three named bounds are ever read, only as own properties, and engine-constructed
  envelopes are built so a polluted prototype cannot smuggle a bound (test48.21,
  test48.22). An accepted non-plain envelope is never treated as carrying inherited
  or widened tolerance: supported own bounds are honored exactly as read, and with
  no supported own bounds it receives zero tolerance.
- **Severity:** LOW — the acceptance fails in the safe direction (an envelope with
  no supported own bounds is zero-tolerance, not widened tolerance; supported own
  bounds are honored exactly, never widened).
- **Recommended resolution:** decide at specification approval whether the stricter
  rule is wanted; if yes, land it as a separate reviewed code change with regression
  tests pinning the Date/Map acceptance shape before and refusal after.
