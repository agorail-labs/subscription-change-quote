## 3. Analysis — can an experimental specification be published while provider-backed commits and full conformance remain unverified?

Yes — provided the publication claims exactly what an experimental specification
publication is, and nothing more. The reasoning:

**What publication asserts.** Publishing v0.6.2 as an *experimental* normative
specification is a claim about **semantics**: "these are the rules the project
commits to as its current, ratified text; implementations can be built and
judged against them; the text itself records what it does not yet decide." It is
not a claim about evidence, artifacts, or operations. Three neighbouring claims
must not be smuggled into it:

- **Conformance certification** — "the reference implementation fully conforms."
  Not made, and not true: three PARTIAL rows and the inherited gaps G-09 stand
  disclosed in the traceability matrix. A publication that carried a conformance
  claim would be blocked by them; an experimental publication that discloses
  them is not.
- **Package release** — "this artifact is published for adoption." A separate
  act with its own metadata and support implications (§4.2).
- **Operational authorization** — "these rules have been exercised against real
  providers and are safe to run." False on this record: no live commit has ever
  been executed, the error allowlist has never met a real error surface (G-10),
  and one adapter carries a structural preservation limitation (G-17). An
  experimental specification does not need operational evidence to be published
  honestly, because it does not assert operability.

**What would actually block an experimental publication.** Two things: (a)
*undecided normative semantics the text depends on* — a published text cannot be
ratified-in-name-only while its load-bearing choices are still open; and (b) an
*undisclosed contradiction between the text and the implementation* — publishing
semantics the code silently disobeys would mislead every reader. The audit
checked both. For (a): every contested choice the text depends on is ratified —
four ratifications, one conditional ratification with its gates spelled out, and
four *ratified deferrals*, where the deferral itself is the decided position and
the text is fail-closed in the interim (§6.17 refuses OPERATION updates; §6.19
refuses unestablishable comparability rather than guessing). For (b): the merged
text was reconciled against the merged code, and every known divergence is
disclosed in the spec's own §9 and in the gap register — including the two that
cut against the project (the legacy-digest residual, G-15/U-14, and the
exclusion-keying behaviour, G-21). A text that carries its limitations in its own
normative front matter does not overclaim by being published with them.

**Residual risk, stated honestly.** The real risk of publication is not
technical; it is *reader inference* — a reader (or a downstream citation)
treating "published specification" as "validated protocol." The mitigations are
cheap and are conditions of the recommendation in §4.1: the experimental
designation stays in the spec status block, the README version block, and the
release title; the release notes carry the known-limitations section unabridged;
and no conformance, adoption, or provider-compatibility language appears anywhere
in the publication change.

**Conclusion of the analysis.** On the audit's classification, nothing that
remains open blocks an *experimental* publication, because every remaining item
limits implementation completeness, provider evidence, or future scope — none
leaves the text's semantics undecided or its claims false. The same items *do*
block the stronger transitions, each for its own reasons (§4.2–§4.4).

## 4. Decisions

### 4.1 Publish v0.6.2 as an EXPERIMENTAL normative specification — **CONDITIONAL GO**

**Assessment.** The specification text is complete, ratified, merged, and
self-disclosing; the audit found no specification-publication blocker (§2, §3).
Publication converts "candidate merged into main" into "the project's current
experimental standard," which is exactly the state the governance record already
supports.

**Conditions (all required; the GO is void if any is dropped).**

1. Publication happens as a **separate, maintainer-approved change** applying
   the §5 checklist (README designation, spec status block, links, tag, release
   notes) — nothing in this decision package activates any part of it.
2. The **experimental designation** is retained in the spec status block, the
   README version block, and the release title.
3. The release notes ship with the **known-limitations section unabridged**
   (§6 draft).
4. **No conformance, adoption, or provider-compatibility claims** appear in the
   publication change, the release notes, or the tag annotation.
5. v0.6.1 remains in the tree, redesignated as the previous version, byte
   unchanged.

**Acceptable limitations (carried by the publication, per §3):** the three
PARTIAL conformance rows; G-09; G-15; G-20; G-21; the ratified deferrals G-14,
G-16, G-18, G-19, G-22 — each disclosed in the spec §9, the traceability matrix,
or the gap register.

**Authorizer:** the maintainer / project owner (Arjun Garg), by approving the
publication change itself. This document recommends; it does not authorize.

### 4.2 Release the reference implementation package — **NO-GO**

**Assessment.** The package is a sound *unpublished* reference (readiness §C:
PASS in exactly that sense). Releasing it — removing `private: true`,
publishing to a registry under a version that asserts v0.6.2 — would make an
artifact claim the record does not yet support.

**Remaining blockers.**

- **Metadata contradicts the release.** Name `@arjun2075/scq-reference`
  (pre-transfer personal namespace — an org-scope decision is required),
  version `0.1.0`, description asserting "SCQ v0.6.1 … not a production billing
  SDK". A release cannot ship metadata that misstates its own specification
  version.
- **Conformance posture.** Three PARTIAL rows and G-09 are acceptable in an
  experimental *specification*; a released *package* invites reliance, and the
  project has not decided whether to close the partials first or to ship with
  them as documented waivers.
- **Ordering.** Specification publication (§4.1) should precede package
  release, so the package can truthfully name the published text it
  implements.

**Required evidence for a future GO:** §4.1 completed; a metadata change
(name/scope decision, version, description) in its own approved PR; an explicit
conformance-posture decision for V62-DET-08 / V62-EVD-01 / V62-SV-02 and G-09
(close, or waive in writing in the release notes); `smoke:pack` evidence on the
release candidate; fresh full-suite counts on the release head.

**Authorizer:** the maintainer / project owner, separately from §4.1.

### 4.3 Authorize a controlled Chargebee test-site commit — **NO-GO**

**Assessment.** Unchanged by the ratification, the merge, or this package. This
is the standing G-12 decision, re-affirmed: a specification-governance act is
not pilot evidence, and no live call of any kind has been made or is authorized
by anything in this record.

**Remaining blockers (PROVIDER-VALIDATION BLOCKERs unless noted).**

- **G-12 condition 1 — UNVERIFIED:** no release approval exists for any exact
  commit.
- **G-12 condition 3 — UNVERIFIED:** no read-only preflight has ever run against
  a real tenant for an exact commit; by definition it cannot be satisfied by
  mocked testing.
- **G-12 condition 4 — BLOCKED:** no named human reconciliation owner.
- **G-12 condition 5 — BLOCKED:** no separate authorization for any exact
  commit; live mutation remains prohibited and `SCQ_LIVE_COMMIT_ENABLED` unset.
- **G-17:** on the Chargebee-live adapter, OPERATION-authorized update commits
  are structurally unenforceable (the sole update mechanism is full
  replacement; no documented conditional write exists). Any future
  authorization would have to be scoped to what the adapter can actually
  preserve, or await a provider mechanism.
- Supporting gaps: **G-05** (origin manifest has no external trust anchor),
  **G-10** (error allowlist never exercised against a real error surface),
  **G-06** (amount-due-only feasibility is an open provider-behaviour
  question), and the A-16-4 Chargebee currency-defaulting behaviour (carried in
  G-16 as a live-readiness concern).

**Required evidence for a future GO:** each G-12 condition satisfied on its own
terms — an exact-commit release approval; a real-tenant read-only preflight for
that exact commit, passing; a named reconciliation owner; and a separate
explicit authorization naming the exact commit — together with a written
disposition of G-17's scope limit and the G-05/G-10 posture.

**Authorizer:** the project owner, per exact commit. No standing or blanket
authorization is recommended under any future GO.

### 4.4 Production use — **NO-GO**

**Assessment.** There is no production evidence of any kind: no live commit has
ever been executed against any provider; the durable layer's guarantees are
stated for a single-writer deployment that has never been operated; no provider
has reviewed, endorsed, or adopted SCQ; and the honest limit recorded throughout
this project stands — the protocol provides tamper-evidence and fail-closed
refusal around provider mutations, not exactly-once provider execution.

**Required evidence for a future GO:** everything in §4.3, sustained over
controlled test-site operation; an operated multi-writer story or an explicitly
accepted single-writer constraint; provider-side engagement on the G-05/G-06/
G-10 questions; and an operational owner. None of this exists today, and none
is scheduled by this package.

**Authorizer:** the project owner, as a new decision on new evidence — not as
an escalation of §4.3.

## 6. Draft release notes — SCQ v0.6.2 (experimental specification)

*Draft text for the §5 publication change; not published anywhere by this
package.*

> **SCQ v0.6.2 — experimental specification**
>
> SCQ v0.6.2 is published as an **experimental** normative specification. It was
> ratified by the maintainer and merged on Oct 31, 2026 (PR #21). Publication
> asserts the semantics below as the project's current experimental text. It is
> **not** a conformance certification for any implementation, **not** a release
> of the reference package (which remains unpublished), and **not** an
> authorization to execute subscription changes against any provider — no live
> provider-backed commit has ever been executed under this specification.
>
> **What v0.6.2 adds over v0.6.1**
>
> - **Fail-closed determinacy (BC-1).** The determinacy gate runs over the
>   quote's participating **financial** dimensions (§3.10, §6.13). Before
>   dispatch, a quote any of whose participating financial dimensions cannot
>   be determined — its value, its provenance, or its comparable units — is
>   refused and does not commit. After a commit, an effect on such a dimension
>   that cannot be established from independent evidence is recorded
>   UNVERIFIED (`COMMITTED_UNVERIFIED`), never claimed as the effect that
>   occurred. The gate proves nothing about effects outside the financial
>   dimensions it assesses, nor about tax, discount, or conversion outcomes.
> - **Candidates are claims, not actuals.** A figure recorded under UNKNOWN
>   determinacy is a *candidate* (§3.10): recorded so that later verification
>   has the original figures to judge, never treated as the effect that
>   occurred. A receipt is verified only against independently established
>   actuals, and the recorded receipt itself is never rewritten by later
>   evidence (§6.15).
> - **Honest timing semantics.** `immediate` names the obligation the change
>   itself *incurs* at its effective time (§3.8.1) — not an invoice total, not
>   an amount presently due, and not cash that has moved; and every committed
>   figure carries explicit provenance stating what it is (§3.11), so a
>   pre-mutation estimate or a provider's claim is never dressed as an actual.
> - **Outcome taxonomy and retry discipline.** Four outcome classes with
>   INDETERMINATE as a terminal, non-retryable recording; re-dispatch is
>   possible only after independently confirmed pre-effect non-execution, under
>   identical request, binding, exclusion, expiry, and fingerprint gates
>   (§6.16).
> - **Authorization preservation (§6.17).** An adapter whose update mechanism
>   cannot preserve the authorization scope a quote was issued under must
>   refuse before dispatch — on Chargebee's full-replacement update path,
>   OPERATION-authorized updates are refused outright.
> - **Runtime proposal validation (§6.18).** One shared validator at quote
>   creation and commit: guarantee modes are exact, tolerance envelopes are
>   shape-checked with own-property reads only, and no code path promotes a
>   malformed proposal to a silent default.
> - **Identity and unit comparability (§6.19).** Effects are established
>   against the subscription the quote was issued for — foreign records are
>   refused before dispatch and never used as evidence after it — and amounts
>   are compared only within an established unit basis; an unestablishable
>   participating currency makes the dimension UNVERIFIED, never silently
>   equal.
> - **Append-only receipt evidence (§6.15).** The recorded receipt is
>   immutable; verification arrives as an append-only evidence trail; the
>   "current" receipt view is derived from that trail, never authored, and
>   promotion to a verified view requires one coherent observed-state basis.
> - **Durable write-ahead layer (§6.16)** with pinned recovery semantics, and a
>   provider-neutral state-verification hook (§6.12).
>
> **Governance.** v0.6.2 was reconciled against the reference implementation
> across PRs #23–#27; its nine contested design dispositions were ratified by
> the maintainer (four ratified, one ratified conditionally, four deferred by
> ratified decision). The full record is in `research/v0.6.2-release-gaps.md`;
> conformance mapping is in `conformance/v0.6.2-traceability.md` (75 rules).
>
> **Known limitations — read before relying on this text**
>
> - Three conformance rows are PARTIAL: snapshot determinacy is emitted but not
>   yet consumed (V62-DET-08); the core trusts adapter-established EXACT source
>   classification and does not independently authenticate provider events
>   (V62-EVD-01 — the specification states this trust limitation itself, §3.11);
>   three adapters use adapter-owned state establishment rather than the shared
>   hook (V62-SV-02). Inherited v0.6.1 test-path gaps (G-09) also remain.
> - A disclosed residual: receipts minted by a pre-fix derivation rule with
>   degenerate observed-state identities whose digests are not enumerable at
>   recovery cannot be re-derived (spec §9, U-14); such identities cannot be
>   minted anymore.
> - Chargebee-bound OPERATION-authorized updates cannot be executed by the
>   reference live adapter at all (G-17); the specification's preservation
>   requirement is enforced there as refusal, which is the intended behaviour.
> - Deferred by ratified decision, fail-closed in the interim: TARGET_REPLACEMENT
>   semantics (G-14), currency/cadence schema extensions (G-16), safe-integer
>   tightening (G-18), strict plain-object envelope enforcement (G-22).
> - The research suite's seven failures are guard-blocked, not layer failures
>   (G-20): the repro harnesses attempt Chargebee-live OPERATION-authorized
>   commits that the authorization-preservation gate (§6.17) refuses before
>   dispatch, so those tests demonstrate the refusal and never reach — and say
>   nothing about — the identity and receipt-evidence layers behind the guard.
>   The probed behaviours are pinned separately by test47, test49, and test50.
> - Finding-7 residuals remain open (G-21): the durable store's dispatch
>   exclusion keys on (quote_id OR subscription_id) with no provider/site
>   predicate, so the same subscription id on two Chargebee sites mutually
>   blocks (over-broad, availability-side; §6.16 states the implemented
>   keying); unblocking an INDETERMINATE attempt (`resolveAttempt`) requires
>   only a free-text operator note, with no structured resolution record; and
>   on the simulator's EXACT/CANCEL branch the committed effect is the quoted
>   effect re-labelled `defined_equal_exact`, recorded from the mutation call's
>   return value with no independent post-commit re-read — the recommended
>   wrong-state negative tests have not been implemented.
> - Envelope nomenclature (G-19): the bound `maxImmediateCreditDecrease` is
>   named and documented as bounding a decrease in immediate *credit*
>   magnitude, but it in fact bounds any favorable net movement of the
>   immediate dimension — a smaller charge with no credit involved consumes
>   the budget exactly as a larger credit does. The mathematics is pinned and
>   unchanged; envelope authors should read the bound by its semantics
>   (favorable-movement magnitude), not by its name.
> - All commit-path evidence behind this specification is simulated or mocked.
>   The error-classification allowlist has never met a real provider error
>   surface, and the origin manifest has no external trust anchor.
