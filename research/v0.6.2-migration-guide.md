# SCQ v0.6.2 — Migration Guide (BC-1 … BC-6)

Status: **candidate-supporting document for a DRAFT specification.** v0.6.2 is not approved,
published, or released; v0.6.1 remains the current specification. This guide describes how
the v0.6.2 candidate (`spec/scq-v0.6.2-spec.md`, §8) changes behavior relative to v0.6.1,
and the **verified current implementation status** of each change, read from the code on
`main` at `82cbd1d` (reconciliation round; originally read at `6f56b05`) (not from issue #7's historical text — issue #7 predates several
milestones, and two of the behaviours it describes as defects were already corrected by
merged migrations before v0.6.2 work began; those are marked ALREADY CORRECTED below and
are not re-migrated).

Summary:

## BC-1 — Fail-closed envelope enforcement

- **Old behaviour (DOC1-corrected citation):** v0.6.1's frozen text contains **no**
  fail-closed enforcement clause — its normative rules end at rule 6.11. The envelope
  lived in v0.6.1 §4.2 (the REVALIDATE clarifications) and rule 6.11 (post-commit
  reconciliation), and the pre-BC-1 core engine's `checkAcceptanceEnvelope` **coerced
  absent values to zero** (unknown-vs-zero coercion), so an UNKNOWN dimension was
  effectively compared as 0 or simply did not participate, and a quote whose
  `immediate` was UNKNOWN was compared on the remaining dimensions and could reconcile
  OK. (§§6.13–6.14 are NEW in v0.6.2 — an earlier draft of this guide misattributed
  them to v0.6.1.) The original defect case (issue #7 Topic 2): a Zuora preview missing
  `immediate`'s determinacy but returning identical figures on both sides produced OK.
- **v0.6.2 behaviour:** §6.13 — when an acceptance envelope is in force, an UNKNOWN
  dimension essential to acceptance requires `QUOTE_NOT_DETERMINISTIC` before any mutation
  or revalidation dispatch; only comparable dimensions are compared, with the v0.6.1 drift
  strings; §6.14 precedence VIOLATED > UNVERIFIED > OK with the no-envelope case explicit.
- **Verified current status:** IMPLEMENTED and in force. `assertEnvelopeEnforceable` runs
  ahead of every adapter's mutation and revalidation dispatch (shared choke point in
  `core/scq-engine.ts`); `reconcileCommittedEffect` implements the precedence. 46 pinning
  tests (test35 ×35, test36 ×11).
- **Affected callers/adapters:** all five adapters (shared engine); durable-path callers
  additionally get the no-intent guarantee (test35.20).
- **Required migration action for callers:** if your quotes can be UNKNOWN on either side,
  expect `QUOTE_NOT_DETERMINISTIC` where v0.6.1-era code proceeded. Quotes that need to
  pass must carry established determinacy (their adapter must label honestly — see BC-2).
  Callers that relied on partial comparison must not reintroduce it.
- **Old receipts/payloads:** receipts recorded before enforcement retain their identities
  and recorded outcomes; replay serves them unchanged (test35.30). They are never
  re-judged to OK by restoration (test35.35).
- **Before/after:**
  - Before: quote `{immediate: absent determinacy, amount 800}` in-envelope, committed
    side byte-identical ⇒ reconciliation **OK** (defect).
  - After: the same quote is refused at acceptance with **QUOTE_NOT_DETERMINISTIC**; in
    reconciliation the same pair yields **UNVERIFIED** (test35.21).
- **Supporting tests:** test35.1–35.7, 35.17–35.21, 35.24–35.29, 35.33; test36 (N/A
  purity).
- **Outstanding incompatibilities:** none known. The `defined_equal_exact` authentication
  limit is a conformance-evidence question (gap G-01), not a behaviour incompatibility.

## BC-2 — Legacy payloads read as UNKNOWN

- **Old behaviour:** determinacy labelling was optional and absence had no defined
  meaning; an implementation could treat a missing label as DETERMINED.
- **v0.6.2 behaviour:** §3.10/§6.13 — absent determinacy ⇒ UNKNOWN for enforcement,
  reconciliation, and audit, on every side and every financial dimension; the `$state`
  merge rule makes a bare-value write unable to mint determinacy.
- **Verified current status:** IMPLEMENTED. `determinacyOf` returns UNKNOWN for missing
  or malformed labels; `auditDeterminacy` reports `UNLABELLED_DIMENSION`; both stores
  apply the merge rule (`quote-store.ts`, `durable-store.ts`).
- **Affected callers/adapters:** producers of quotes/revalidations/commits (all five
  adapters updated to label from evidence); any external payload producer feeding the
  reference implementation.
- **Required migration action:** label determinacy from evidence at construction. Do not
  post-process labels onto payloads you did not produce — a label is a claim, not a fix.
- **Old receipts/payloads:** legacy quotes (no labels) remain loadable and their receipts
  replay identically, but for any *new* acceptance/reconciliation they read as UNKNOWN
  and therefore cannot pass an envelope gate (test35.5/35.6) or reconcile to OK
  (test35.35). **They cannot be safely upgraded**: there is no procedure that turns a
  legacy payload into verified determinacy after the fact; re-quoting through a current
  adapter is the only path.
- **Before/after:** legacy quote `{immediate: {amount: 800}}` — before: comparison
  proceeded as if DETERMINED; after: UNKNOWN ⇒ refusal/UNVERIFIED as above.
- **Supporting tests:** test35.5, 35.6, 35.31, 35.35; test14–16 (PR #8 suites).

## BC-3 — Stripe simulator `amount_due` mapping removed

- **Old behaviour (historical, pre-Oct 2026):** the Stripe simulator mapped the preview's
  `amount_due` (invoice amount presently due) into `CommercialEffect.immediate`.
- **v0.6.2 behaviour:** §3.8.1 — `immediate` is the obligation INCURRED; for the Stripe
  preview the incurred amount is the preview's incurred figure; `amount_due`, totals, and
  credits travel in provider metadata, never in the effect.
- **Verified current status:** **ALREADY CORRECTED** in merged PR #10, before v0.6.2
  work; no action in this migration. Current code: `adapters/stripe-adapter.ts` derives
  `immediate` from `preview.incurred_amount` and labels it UNKNOWN when the preview
  withholds the incurred figure (the Chargebee-similar honest fallback); committed actuals
  come from the committed invoice's own figures; CANCEL quotes cite the (CANCEL,
  immediate) N/A licence with the field absent.
- **Affected callers/adapters:** Stripe simulator only.
- **Required migration action:** none. Callers consuming Stripe-simulator quotes should
  already see incurred-based `immediate`; if a consumer still treats `immediate` as
  amount-due, that consumer is wrong under both v0.6.1's §3.8 text and v0.6.2's.
- **Old receipts/payloads:** receipts produced by the pre-correction simulator carry the
  old (mis-mapped) figures; they retain their identities and are not recomputed. Do not
  cite them as evidence of incurred amounts.
- **Before/after:** preview with incurred 1200, amount_due 300 (credits applied) —
  before: `immediate = 300`; after: `immediate = 1200`, `amount_due = 300` visible only
  in provider metadata.
- **Supporting tests:** test17 (migration suite), test18 (review corrections).
- **Outstanding incompatibilities:** none.

## BC-4 — Paddle reconciliation basis moves to provider actuals

- **Old behaviour (historical):** the Paddle simulator revalidated by re-running its
  preview and reconciled against that figure, so a committed effect could be "verified"
  by the adapter's own recomputation.
- **v0.6.2 behaviour:** §3.11/§6.14 — committed facts are established only from
  provider-retrieved actuals bound to the mutation (the persisted transaction's id); a
  revalidated preview figure is quote-side evidence (`revalidated_preview`) and never
  establishes a committed fact; failed verification reads after a landed mutation yield
  COMMITTED_UNVERIFIED from data in hand (doctrine P1).
- **Verified current status:** **ALREADY CORRECTED** in merged PR #11, before v0.6.2
  work. Current code: `adapters/paddle-adapter.ts` persists transactions, retrieves them
  by the mutation's own id (`retrieveTransaction`), and labels unverified candidates
  `unestablished` without further reads; the store brands the evidence before the receipt
  can move.
- **Affected callers/adapters:** Paddle simulator only.
- **Required migration action:** none.
- **Old receipts/payloads:** pre-correction receipts that claimed verification from
  revalidation lineage are historical records; they are not re-judged, but they must not
  be cited as §3.11-conformant evidence.
- **Before/after:** commit returns transaction `txn_…`; verification read fails —
  before: adapter re-ran preview and reconciled OK; after: receipt is
  **COMMITTED_UNVERIFIED**, recording the mutation response's figures as labeled
  candidates (UNKNOWN determinacy, `unestablished`) — present for later verification,
  establishing nothing (see the SPEC3 cross-cutting clarification below).
- **Supporting tests:** test19 (migration suite incl. P1/P3), test20 (review
  corrections), test35.22/35.23 (the cross-adapter pins for estimate/revalidation
  lineage).
- **Outstanding incompatibilities:** none.

## BC-5 — `ReconciliationResult` union widened with UNVERIFIED

- **Old behaviour:** `ReconciliationResult.status` was `OK | VIOLATED`; incomplete proof
  had no honest value and collapsed toward OK.
- **v0.6.2 behaviour:** §6.14 — status is `OK | VIOLATED | UNVERIFIED` with the stated
  precedence; VIOLATED from established facts is preserved beside UNKNOWN dimensions.
- **Verified current status:** IMPLEMENTED (type widened in `core/types.ts`; precedence
  in `reconcileCommittedEffect`; receipt status union widened to carry UNVERIFIED in
  PR #8).
- **Affected callers/adapters:** every consumer of reconciliation results and receipts —
  this is the one change most likely to break downstream exhaustive switches.
- **Required migration action:** handle UNVERIFIED explicitly. Treat it as "do not act
  as if verified," never as OK; VIOLATED remains the only value that asserts a breach.
- **Old receipts/payloads:** receipts recorded with OK under the old union keep that
  recorded value (history is immutable); a *fresh* reconciliation of the same pair under
  v0.6.2 may return UNVERIFIED. Both statements can be true; consumers must not rewrite
  the recorded receipt.
- **Before/after:** committed side UNKNOWN, quoted side DETERMINED — before: **OK**;
  after: **UNVERIFIED** (test35.21). Established overage beside an UNKNOWN dimension —
  before: ambiguous; after: **VIOLATED** (test35.26).
- **Supporting tests:** test35.21, 35.24–35.26; test14–16.
- **Outstanding incompatibilities:** downstream exhaustive handling (above) is the
  caller's migration duty; the reference implementation's own consumers were updated in
  PR #8/#19.

## BC-6 — Retry rules: INDETERMINATE vs CONFIRMED_NON_EXECUTION

- **Old behaviour:** dispatch failures had no protocol-level taxonomy; a caller could not
  distinguish "provably never ran" from "may have run," and nothing forbade a blind retry
  after a lost response.
- **v0.6.2 behaviour:** §3.12/§6.15/§6.16 — four outcomes; INDETERMINATE forbids
  automatic re-dispatch, is never re-armed, and requires operator reconciliation over
  the whole store. CONFIRMED_NON_EXECUTION (demonstrably pre-effect) permits **one
  re-dispatch under the same quote and the same idempotency key** per settlement,
  gated on: identical canonical request + request hash; the key's
  quote/subscription/provider/site binding unchanged and matching the durably stored
  quote; the same-subscription exclusion re-checked inside the authorizing
  transaction; and the ordinary commit preconditions (expiry, subscription
  fingerprint) applied to the re-dispatch presentation exactly as to a first dispatch.
  Terminal COMMITTED_* attempts serve their recorded receipt/outcome and are never
  re-armed. Verification-failure-after-landing yields COMMITTED_UNVERIFIED, never
  INDETERMINATE. *(SPEC2: an earlier draft of the candidate said CONFIRMED_NON_EXECUTION
  is retried "as a new quote" — that contradicted the merged ledger and has been
  corrected to the implemented doctrine, recorded as OPEN DECISION G-13 for
  ratification at approval; the fresh-quote/key alternative is named there.)*
- **Verified current status:** IMPLEMENTED for the Chargebee-live adapter and the durable
  layer (PR #16 L1–L3 + PR #17, incl. finding D2's in-transaction exclusion re-check on
  the re-dispatch path): the L2/L3 evidence gate (demonstrable pre-effect failure
  + HTTP 400 with an allowlisted code for request-level refusals; ambiguous classes stay
  INDETERMINATE), the durable attempt ledger's retry blocks and its single bounded
  re-dispatch, and the coordinator's settle-INDETERMINATE path. Pinning tests:
  test29.8 (D2a — re-dispatch blocked while a same-subscription attempt is unresolved),
  test29.9 (D2b — the legitimate re-dispatch succeeds), test29.10 (D2c — key never
  re-associated), test27.20 (same key, different request refused). The four simulators classify their failures pre-dispatch by
  construction (their "dispatch" is in-process), which conforms trivially.
- **Affected callers/adapters:** Chargebee-live adapter callers; any caller driving the
  durable coordinator. Simulator callers see no behaviour change.
- **Required migration action:** callers of the live adapter must handle INDETERMINATE as
  a stop-and-reconcile state, not an error to retry; callers must supply the durable
  store + coordinator wiring (mismatched wiring is refused, test29/30).
- **Old receipts/payloads:** outcomes recorded before the taxonomy existed are historical;
  a pre-taxonomy receipt carries no outcome classification and must not be read as
  CONFIRMED_NON_EXECUTION.
- **Before/after:** mutation POST times out; the subscription now shows the target state —
  before: caller free to retry (double-effect risk); after: **INDETERMINATE**, retry
  refused, receipt reconciled by operator review (test26 L1; rehearsal rh-05).
- **Supporting tests:** test26 (L1–L3 suites), test27/28/29/30 (durable layer), test38
  (rehearsal, pilot evidence).
- **Outstanding incompatibilities:** **no live-network evidence** — the classification has
  only ever run against mocked transports; Chargebee's real error surface may contain
  classes the allowlist has not seen (they fail closed to INDETERMINATE, which is safe
  but may surprise operators). Recorded in the gap register (G-10).

## Cross-cutting refinement — EXACT equality (SPEC1; companion to BC-5/BC-6)

Not a BC item, but a wording migration every consumer of EXACT receipts must absorb:
v0.6.1 §3.8 required `quotedEffect` to **deep-equal** `committedEffect` for EXACT.
That sentence was written before role-specific committed provenance existed. Under
v0.6.2 §3.11, a conforming EXACT committed effect is *constructed* from the quoted
effect by adding committed-side evidence metadata — Stripe's adapter adds
`provenance.committedSource: "defined_equal_exact"`; Paddle's additionally refines the
committed-side recurring provenance note with the post-commit verification kind — so
whole-object deep equality is unsatisfiable for exactly the receipts the evidence
contract requires. **v0.6.2 §3.9 therefore defines EXACT equality over the covered,
economically relevant dimensions** (each covered dimension's value, determinacy, and
timing/term coverage), and states explicitly that whole-object deep equality
(`JSON.stringify` equality) is **not** a conformance criterion. Migration action: any
consumer comparing whole receipt effects for EXACT conformance must switch to the
covered-dimension comparison (§6.13's comparable/skipped assessment); consumers
comparing only the covered dimensions are unaffected. Rule: V62-EVD-07; controls:
test17.12, test19.15, test19.11a/19.11b. The separate question of whether the
`defined_equal_exact` label can be *authenticated* is unchanged and remains OPEN
(G-01) — equality of dimensions is not authentication of source.

## Cross-cutting clarification — unverified candidates on COMMITTED_UNVERIFIED receipts (SPEC3; companion to BC-4/BC-5)

Not a BC item, but a terminology rule every consumer of receipts must absorb. When a
mutation has landed but independent verification is unavailable, the merged adapters
record a COMMITTED_UNVERIFIED receipt whose committed effect may carry numerical
figures on UNKNOWN dimensions. Those figures are **candidates**, not established
actuals: determinacy stays UNKNOWN, `committedSource` is `unestablished`, the
provenance note discloses the source, and reconciliation is UNVERIFIED. The
construction is deliberate (PR #10/#11 doctrine P1): the candidate preserves the
ORIGINAL figures so a later independent verification (§6.15) has a record to verify
against — **as originally written; superseded by the reconciliation round (A-17-1,
PR #27 as merged):** later evidence establishes the dimension independently, differing
established actuals are recorded in the append-only evidence record and judged against
the quote/envelope (verified-with-violation where they fall outside it), and
candidate≠actual is never a conflicting receipt identity. The recorded candidates
remain part of the receipt's identity and are never rewritten. Candidates occur in
all five adapters, from exactly two sources: the mutating call's own response
(verification re-read unavailable), or — for cancellations — the quote's
post-cancellation level. An earlier draft of the candidate stated the §3.10 no-number
rule categorically and required committed effects to contain only established figures;
that wording declared this merged construction nonconforming and has been corrected:
§3.10 now scopes the categorical rule to quote/revalidated roles (fail-closed
enforcement unchanged — test35.7 still pins that a number under UNKNOWN rescues
nothing at the gate) and defines the committed-role candidate carve-out (§3.10,
§3.12; rule V62-EVD-08). **Migration action:** consumers MUST NOT present a candidate
as a verified, reconciled, or charged amount; consumers that display committed figures
from COMMITTED_UNVERIFIED receipts must carry the UNKNOWN/`unestablished` labeling
through. Controls: test26.17 (Chargebee-live no-reread case + later verification
against the recorded candidates), test17.10, test19.12, test20.1–20.3, test24.14,
test24.25, test25.11/25.11b, test25.20; no-false-OK pins: test35.29, test35.21.

## Reconciliation additions (PRs #24–#27 — normative additions, not BC items)

These merged behaviours postdate the BC-1…BC-6 design and are specified in the
reconciled candidate (§3.15/§3.16, §6.15–§6.19). None of them changes a v0.6.1 rule;
each is a new v0.6.2 obligation with its own migration surface:

| Addition | Status | Migration position |
|---|---|---|
| Authorization preservation (§6.17, PR #24) | **MERGED** | Chargebee-live OPERATION-authorized update commits now refuse pre-dispatch (`AUTHORIZATION_PRESERVATION_UNENFORCEABLE`, CONFIRMED_NON_EXECUTION semantics) instead of dispatching a full-list replacement. Callers relying on those commits must treat the refusal as terminal for that quote/mechanism; TARGET_REPLACEMENT is refused at creation. This is the standing preservation blocker (gap G-17), not a transitional state. |
| Runtime proposal validation (§6.18, PR #25) | **MERGED** | Malformed proposals/envelopes that previously flowed to provider calls (or were coerced) now refuse at creation and at commit over the stored record (`INVALID_PROPOSAL`); post-commit, a malformed envelope classifies instead of throwing. Callers must fix malformed inputs rather than rely on coercion. Safe-integer bounds and the quantity-0 ruling remain OPEN (G-18). |
| Identity binding + unit comparability (§6.19, PR #26) | **MERGED** | Foreign-subscription reads/evidence can no longer verify a commit; cross-currency/cadence comparisons classify on the units (VIOLATED on contradiction, UNVERIFIED when unestablishable) instead of on raw numbers. The immediate-currency schema extension (A-16-3) is NOT adopted — see G-16 for the undecided set. |
| Receipt-evidence model (§6.15/§6.16, PR #27) | **MERGED** | Stored receipt records gain an append-only evidence trail and a derived current view. Legacy one-transition trails restore by normalization and re-derivation (a legacy verified label over unestablished figures restores truthfully, not as recorded). Recorded receipts are never rewritten; §6.10 replay is byte-equivalent after verification (test50.4). Stored `observedStateDigest` values are stated fields — the legacy degenerate-digest limitation and its enumerable-refusal rule are gap G-15. Consumers reading only the recorded receipt see commit-time truth; the current view is a separate read. |

## Cross-cutting migration invariants (verified)

1. **Old receipts retain their original identities.** Receipt identity
   (`receiptIdentityFields`/`receiptIdentityDigest`) is enforced on restore and replay;
   a conflicting identity is refused, never overwritten (test14–16, test15/16 suites).
2. **Restoration cannot upgrade UNKNOWN evidence into verified financial actuals.** The
   recorded receipt and the current view are separate records; restore applies the same
   determinacy merge rule and coherence checks; a legacy committed-UNVERIFIED receipt
   restores as UNVERIFIED and a fresh reconciliation of its pair yields UNVERIFIED, not
   OK (test35.31, test35.35).
3. **No silent re-labelling.** Determinacy labels are written only by the component that
   produced the figure, from its evidence; the stores' merge rule makes a later bare
   write unable to mint or upgrade a label.
4. **Nothing in this guide authorizes a live mutation.** Migration status describes the
   reference implementation's behaviour under simulation and mocked transports; the
   test-site commit decision remains NO-GO (see `research/v0.6.2-release-readiness.md`).
